建模取舍（design notes）

这篇回答"为什么这么做"，而不是"做了什么"。做了什么看 README， 公式与缺口看 physics.md。 发布时这是给 HN / r/RadioFrequency 那类读者看的：他们信的是取舍，不是功能列表。

1. 为什么把"观测"当核心，而不是把"杀伤"当核心

大多数兵棋的结算终点是"命中/未命中"。这里的终点是对方能拼出多准的一张图： 频率、到达角、到达时间、功率，各自带噪声、带漏检、带虚假目标，再融合成位置估计与协方差。

这个选择决定了后面所有技术路线：必须有概率化测量（不是布尔可见性）， 必须有事件日志（不然没法复盘"你是从哪一刻开始暴露的"）， 必须有确定性重放（不然"这次为什么输"永远说不清）。

2. 为什么确定性是地基，而不是优化项

规格里写的是"固定步长 + seeded RNG + 事件日志"，落地时拆成三条硬约束：

约束 实现 为什么不能妥协
时间 t = index · dt，不累加 浮点累加会漂，漂了就没法逐帧对齐
随机 单一 default_rng(seed)，只用于检测掷点 任何一处隐式随机都会让 replay 失效
日志 一行一事件、sort_keys、每行自包含 可比对、可哈希、可单独解析

代价是：每次跑都要把状态序列化一遍（replay 比快照大），且不能随手用 random.random()。收益是：同一想定 + 同一 seed，sha256 完全一致—— 这条有单测直接守着（test_standoff_run_is_deterministic）。

3. 为什么物理只有一份，前端只做插值

规格说"一个内核三个面，不许前后端各写一套"。T2 又要求无后端。 两条同时成立的唯一做法：

Python（唯一物理实现） --export-web--> (Rt, Rj) 查表 --插值--> 浏览器

代价：页面的数值是插值出来的，边界处有几 % 的误差； 代价：想改物理必须重新导出数据包。 收益：网页上的数和 CLI 上的数不可能对不上——这类不一致最伤可信度。

表用 base64 float32（126 KB），而不是 JSON 浮点数组（体积 ×4）； 两个轴都是 geomspace，所以插值必须在 log 空间做，否则近距段会明显失真。

4. 为什么是 Swerling I 闭式，不是更精确的模型

Pd = Pfa^(1/(1+SNR)) 是闭式、可反解、在 Pfa 和 SNR 上单调的近似。 它的形状对 SNR 很钝：Pfa = 1e-6 时要约 21 dB 才到 Pd = 0.9，而不是经验直觉的 13 dB。

这不是 bug，是选择的代价。选它是因为：

  • 能反解出"检测距离"的闭式（见 physics.md §3.5），引擎每个 tick 不用迭代；
  • v1 要的是"能讲清楚的一条曲线"，不是"能对表的一条曲线"。

如果哪天要做检测概率对 Pfa 的精细权衡，应该换 Marcum Q / Swerling 精确式， 并同时把反解改回数值方法——这是一次有明确边界的替换，不是"逐步逼近真值"。

5. 为什么没有处理增益（以及它的代价）

v1 不含脉压、相干积累、MTI/PD 滤波。后果很直接：干扰效能被高估。

以 02_standoff 为例，1 W 的噪声干扰机、100 MHz 带宽就能把 12 km 处的目标压到 Pd = 3e-4。看着不合理，但在"没有处理增益"的模型里它是自洽的： 落进 2 MHz 接收机的只有 20 mW，而 12 km 处回波本身只有约 -67 dBm（噪声底 -108 dBm）。

这个缺口写在 physics.md §7.1，也在 README 里点明了。 发布文案里必须主动说这件事，否则懂行的人第一眼就会认定"模型是错的"。

6. 为什么 J/S 用 SINR 口径

SNR = Pr / (Pn + Pj_rx)，干扰进分母。这样"干扰压制"和"检测概率下降"是同一条链， 而不是两个互不相干的指标。代价是 Pd 对干扰功率非常敏感（J/S = 1 就把 SNR 砍半）， 收益是"烧穿 ≠ 能检测"这个反直觉结论是从模型里长出来的，不是编的。

7. 为什么 R_bt 只有一个 G

规格里原本写 R_bt ∝ G²。按同一节的 Pr 与 Pj_rx 联立，接收增益 Gr 在两条支路里 相消，结果应该只有一个 G（发射增益）。差异是 sqrt(G)——35 dB 时约 56 倍， 测试不可能同时满足。

处理方式：改公式、在代码注释与 physics.md §4.1 写清推导、在 PROJECT.md 留下修正记录， 并写两条回归测试钉住"J/S 与接收增益无关""J/S 与波长无关"。 规格与实现冲突时，先算出谁对，再改，并留下证据——这条比公式本身更值得记。

8. 为什么是 canvas 自绘，不是 deck.gl

T2 的验收是"拖动 + 热力图 + 曲线 < 100 ms"。二维、几百个图元、一张 220×220 的 低分辨率热力图放大——canvas 足够，打包产物 230 KB（gzip 73 KB），零 WebGL 依赖。

deck.gl 的优势在成千上万条轨迹与 GPU 聚合，v1 没有这种数据量。 等 T3b 要做多平台大规模态势时再上，届时数据包结构不用变（表还是表）。

9. 现在明确不做的事

  • 真实装备参数库（拿不到，也不该有）
  • 多径 / 地形遮蔽 / 大气吸收
  • 欺骗干扰、脉冲干扰、扫频干扰
  • 航迹状态机（M-of-N）——所以 detected=False 只代表"这一帧漏了"，不代表"丢批"
  • 3D 渲染、联网对战、LLM

10. 如果重来会怎么改

  1. 先写 metrics.md 再写物理：Pd 的"单次照射 vs 累计"口径差点在实现里混掉。
  2. 把 replay schema 当接口先定死：一开始 link 与 detection 分两条事件， 事后加 detection_ring_m 时才发现动画依赖它。
  3. 早一点做截图验证：两个真 bug（坐标单位错位、红环画在红底上）都是渲染出来才暴露的， 单测和类型检查全绿也发现不了。
