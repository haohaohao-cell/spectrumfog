﻿# SpectrumFog / 频谱迷雾

在线试用：haohaohao-cell.github.io/spectrumfog · 文档站：…/spectrumfog/docs · 排行榜：…/docs/leaderboard.html —— 拖动干扰机，看雷达覆盖怎么塌。纯静态，无后端。

一个部分可观测的电磁对抗仿真平台：双方都只能看到被干扰污染、被聚合过的频谱态势， 必须靠定位与识别反推对手的辐射源在哪、是什么。

不是"算杀伤"的兵棋，是"算认知"的环境。

spectrumfog sim scenarios/02_standoff.yaml --gif 直接生成：干扰机从 60 km 压到 4 km， 雷达的跟踪边界从 20.5 km 收缩到 5.3 km，12 km 处的目标在 t = 170 s 丢失。 右上曲线是模型概率 Pd，灰色阶梯是单次照射的抽样结果。

一条命令跑起来

python -m venv .venv
. .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -e .

spectrumfog sim scenarios/02_standoff.yaml --gif   # 跑仿真 → replay.jsonl → GIF
spectrumfog run scenarios/01_duel.yaml             # 静态曲线：烧穿 / Pd–距离 / J/S–距离

如果 spectrumfog 不在 PATH 里（Windows 上 pip 的 Scripts/ 目录常常不在）， 等价写法是 python -m spectrumfog ...。

命令 产出
spectrumfog sim <yaml> out/<name>.jsonl（一行一事件的 replay）+ 终端摘要
spectrumfog sim <yaml> --gif 再加一段俯视动画 out/<name>.gif
spectrumfog animate <jsonl> -o x.gif 只读 replay 重出动画（viz 不碰引擎）
spectrumfog run <yaml> 三张静态图 + 链路指标
spectrumfog export-web <yaml> -o data.json 前端数据包（T2 用，见下）
spectrumfog aar <jsonl> 复盘报告：时间线 + 暴露时长 + 归因（单页 HTML）
spectrumfog bench --all baseline 策略评测表（Gymnasium 环境，见下）
spectrumfog bench --suite … --submit 生成可校验的排行榜提交物
spectrumfog bench --verify <json> 校验提交物与当前想定是否一致
spectrumfog bench --leaderboard submissions 汇总排名

三个反直觉的结果（免得你以为算错了）

1. 烧穿 ≠ 能检测。 01_duel（150 kW / 35 dBi 雷达，90 W 干扰机在 30 km）里， J/S = 1 的烧穿半径是 3.24 km，但干扰下真正还能维持 Pd = 0.5 的距离只有 0.75 km——差了 4 倍多。 因为 J/S = 1 只是把信噪比砍掉 3 dB，而这里的 Swerling I 闭式要 Pd = 0.5 得约 20 dB。 "目标在烧穿圈内"不等于"雷达看得见它"。

2. 1 W 干扰机能压制 150 kW 雷达。 02_standoff 里，1 W 干扰机在 60 km、 目标在 12 km。因为想定默认关闭了处理增益（脉压、相干积累、MTI）： 100 MHz 上摊开的 1 W 落进 2 MHz 接收机只剩 20 mW，而 12 km 处的回波本身只有 −67 dBm， 噪声底是 −108 dBm。这个数字是"没有处理增益"这个前提的产物，不是仿真结果。

3. 光有 20 dB 处理增益还不够。 07_gain 与 01_duel 同一组参数，只把 processing_gain_db 从 0 提到 40：J/S 从 85.6 掉到 0.0086，Pd 从 1e-6 升到 0.85， 601 帧里从 0 次命中变成 505 次。但中间那一档 20 dB 只把 J/S 压到 0.86， 601 帧只命中 2 帧——"加 20 dB 就翻盘"是错觉，要压回去大约需要 40 dB。

这三条都是 docs/design.md §5–§6 里写明的取舍， 完整缺口清单在 docs/physics.md §7（处理增益默认关、无多径地形、无航迹状态机）。

Web 交互（T2）

拖动干扰机，覆盖热力图、跟踪边界和两条曲线实时跟着变；没有后端。 物理仍然只有 Python 这一份：export-web 把 Pd/J-S 编译成 (Rt, Rj) 查表， 网页只做插值和画图。

spectrumfog export-web scenarios/02_standoff.yaml -o viz/web/public/data.json
cd viz/web && npm install && npm run dev      # http://localhost:5173
npm run build                                 # dist/ 纯静态，可丢 GitHub Pages

数据包格式与"为什么前端不算物理"写在 docs/web.md。

初始状态：干扰机在 60 km，12 km 处的目标仍被跟踪（Pd 0.92），跟踪边界 20.5 km。 把红色方块往雷达方向拖，边界和蓝色区域会一起收缩。

AAR 复盘（T3a / T3b+）

replay.jsonl 进，单页 HTML 出：关键事件时间线、暴露时长、定位误差归因。 结论句是自动生成的，每个数字都能由日志行复算：

你的 jammer_b 在 t = 4 s 被有效定位（CEP ≈ 74 m，门槛 500 m）。 t = 0 s 其实已经首次交汇，但当时只有 2 台传感器参与（交会角 82°）、CEP 611 m 还没进门槛； 真正锁定它的是 esm_1、esm_2、esm_3 的 3 条量测同时交汇； 留一检验里去掉 esm_2 会让误差从 152 m 变成 3318 m； 精度主要由 TDOA 决定（只留测向 CEP 1683 m，只留 TDOA 137 m）。

spectrumfog sim scenarios/01_duel.yaml --out out     # 出 replay
spectrumfog aar out/01_duel.jsonl                    # 出 out/01_duel_aar.html

两份想定都能复盘，结论完全不同：

想定 首次有效定位 暴露时长 最精确 为什么会这样
01_duel（固定站位） 4 s 328 s 13 m 三站同帧交汇，精度由 TDOA 撑起（只留测向 CEP 1683 m）
02_standoff（干扰机 60→4 km） 44 s 90 s 11 m 前 40 秒只有零星截获，凑不齐同帧两站；越近越准

02_standoff 前 44 秒没被有效定位，不是模型坏了：1 W 的干扰机在 60 km 处 SNR 只有 11， 收得到、定不准；等它压进 20 km 以内，同帧两站交汇才有意义，CEP 从 461 m 收敛到 11 m。 反过来，降功率确实更隐蔽——01_duel 里把 90 W 降到 9 W，对方就再也定不进门槛 （最好 943 m > 500 m），代价是压制效果也弱了。

"原因是 X" 不是形容词：留一法逐台去掉传感器重解一次，外加"只留测向 / 只留 TDOA" 两组对照，都是同一套最小二乘，所以归因结论和定位结论不可能不一致。

报告现在还会给出航迹：蓝方在 t=3 s 起批、t=99 s 丢失、确认覆盖 85%。 这是和"单帧解出位置"不同的问题——航迹要连续命中 3 次才算确认， 确认后还能滑行 5 帧，所以"漏一帧"和"跟丢了"终于是两件事。

三条硬约束（PROJECT.md §2，改之前先想清楚）：

  1. 确定性优先：固定步长 + seeded RNG + 事件日志；同一 seed 的 replay 逐字节相同。
  2. 引擎与表现分离：spectrumfog 内核不 import 任何 UI 库；viz 只读 replay。
  3. 一个内核，三个面：CLI / Web / Gym 共用同一份物理，不许各写一套。

内部一律 SI（W / m / Hz / s / rad）；dB、km、MHz 只允许出现在 YAML 输入和终端输出。
